## 0. 名词约定（先统一，避免歧义）

项目里“联系人列表 / 可会话列表 / 角色目录”长期混用，先固定四个名字：

| 名词 | 含义 | 数据来源 |
| --- | --- | --- |
| 角色库（联系人目录） | 全部角色与群组的原始库 | `data/chat_contacts.json`（83 条：73 角色 + 10 群组） |
| 联系人列表（页签） | 右侧编辑面板的新页签，显示可加入会话的角色/群组，是“来源列表” | 阶段 A：`/api/contacts` 的全部启用联系人；未来：`data/conversation_contacts.json`（只存 ID） |
| 会话列表（预览目录） | 预览界面上真正显示、可切换的会话条目，是“目标列表” | 阶段 A：全部启用联系人（保持现状）；未来：用户双击加入的卡片 |
| 项目联系人快照 | 单个项目保存的历史联系人信息 | 项目 `project.json` 的 `contact` 字段 |

页签显示名已定稿为「联系人列表」（不用“可会话角色列表”）；左侧那份继续叫「会话列表」或「预览目录」。
阶段 A 两份列表内容相同（都是全部启用联系人）；阶段 B 起两者分离：右侧是来源，左侧是目标。

## 2. 草拟数据模型

### 2.1 新文件 `data/conversation_contacts.json`

只保存已加入列表的 contact ID，不复制名字、头像等详情。草拟结构：

> 阶段 A 先落地 `version: 1` 的 `contact_ids` 一个数组；为什么将来要加 `preview_ids`、
> 以及“共用清单”的取舍，见 2.3。

```json
{
  "version": 1,
  "updated_at": "2026-10-06T00:00:00Z",
  "contact_ids": [1036, 1076, 9001, 9200]
}
```

字段说明：

- `version`：整数，结构版本，便于将来迁移。
- `updated_at`：ISO 时间字符串，仅用于排查，不参与逻辑。
- `contact_ids`：有序数组，元素为整数 ID；顺序即列表展示顺序（后续可支持拖拽排序）。

读取规则：

- 文件不存在时视为“首次升级”或“未开工”，运行时默认把所有当前启用联系人写入清单，避免列表突然为空。
- 清单里的 ID 在 `chat_contacts.json` 中找不到（角色被删、被禁用）时，读取阶段直接过滤，不报错、不清空文件。
- 写入时只写 ID，不写入任何联系人详情。

### 2.2 与前缀数据的边界

- `data/chat_contacts.json`：基础角色库，保持只读、不改写。
- `data/group_members.json`、`data/custom_groups.json`：群组目录，保持原有读取逻辑。
- `data/conversation_contacts.json`：本次新增的用户清单，是唯一的持久化筛选层。
- 项目 `contact` 快照：只读兼容，不因移除联系人而改写。

状态单独检查已确认：`data/group_members.json` 顶层的 `note` 提到 `deleted_group_ids`，但实际文件没有该键，读取时按“缺失即可”处理。

### 2.3 「清单文件共用」到底在问什么（讲解）

#### 2.3.1 文件是什么

`data/conversation_contacts.json` 是**只存 ID 的持久化文件**，回答“哪些角色/群组属于本次会话编辑范围”。
它不保存名字、头像、群成员，那些仍然从 `chat_contacts.json` 读。所以它本质上是一份“名单”，不是一份“资料”。

#### 2.3.2 为什么会有“共用”这个问题

按你刚定下的规则，界面上同时存在两份名单：

1. **右侧「联系人列表」页签** = 来源。可搜索、可分页，里面是可以被加入会话的角色/群组。
2. **左侧「会话列表（预览目录）」** = 目标。真正出现在手机预览里、可以进入对话编辑的条目。

两份名单在阶段 A 内容一样（都是全部启用联系人），但阶段 B 之后会分家。
于是就有个问题：**这份 `conversation_contacts.json` 到底记录哪一边？还是两边都记？** 这就是“共用”的意思。

#### 2.3.3 三种方案

方案 A：**一份名单，两边共用**（文件里只有 `contact_ids`）。

- 语义：右侧页签就是“会话列表的镜像”，页签里有什么，预览里就有什么。
- 优点：结构最简单，只有一个真相来源，不会出现“在列表里但预览没有”的状态。
- 缺点：做不到“库里先攒 80 个，只挑 5 个放进预览”的两步流程；双击就等于直接进预览，移出也同时从两边消失。

方案 B：**两份名单，两个文件**（`conversation_contacts.json` + 新建 `preview_contacts.json`）。

- 语义：来源和目标各存一份，互不覆盖。
- 优点：职责清晰，将来想单独重置预览、单独导入来源都方便。
- 缺点：两个文件要各自处理版本、原子写入、默认生成；两边 ID 不一致时还要额外定义“以谁为准”。

方案 C：**一份文件，两个数组**（推荐）。

```json
{
  "version": 2,
  "updated_at": "2026-10-06T00:00:00Z",
  "contact_ids": [1036, 1076, 9001, 9200],
  "preview_ids": [1036, 9200]
}
```

- `contact_ids`：右侧「联系人列表」的来源名单。
- `preview_ids`：左侧「会话列表（预览目录）」的目标名单。
- 优点：两个集合都有归属，但读写、版本迁移、原子落盘只有一套代码；
  `version` 从 1 升到 2 时，若旧文件没有 `preview_ids`，读取阶段默认 `preview_ids = contact_ids`，旧数据不丢、不会突然清空预览。

#### 2.3.4 现在该做哪一步

- **阶段 A（本次）**：按方案 C 的 `version: 1` 先落地 `contact_ids` 一个数组即可，等于“来源名单”。
  此时预览目录保持现状（渲染全部启用联系人），不读 `preview_ids`，所以行为零回归。
- **阶段 B（改预览目录时）**：把 `version` 升到 2、加 `preview_ids`，双击写入 `preview_ids`，预览目录改读它。

这样文件只建一次，将来加字段是向后兼容的升级，不需要再新建文件，也不需要迁移历史数据。

## 3. 界面与交互原理

### 3.1 右侧编辑面板加页签

在 `.editor-column` 顶部加一条页签栏，本次至少两个页签：

- 「编辑」：现有三个区块（项目与联系人 / 消息列表 / 消息属性）。
- 「联系人列表」：本次新增的角色目录页签（已定稿）。

原理：

- 只切换右栏内容的可见性，不重建 DOM 树，避免影响已有编辑状态。
- 页签状态存在前端内存中（例如 `state.editorTab`），刷新后回到默认「编辑」。

页签顺序：`编辑` 在前（默认页签），`联系人列表` 在后。新增功能默认追加到末尾，不插到「编辑」前面。

#### 3.1.1 为什么用页签而不是继续堆叠

右侧编辑面板当前是纵向堆叠的单列滚动（项目与联系人 / 消息列表 / 消息属性）。
每加一个功能就只能继续往下堆，用户需要长距离滚动；且各功能彼此独立，很少需要同屏对照。
页签把“互斥的功能区”横向切开，更适合后续连续加功能：

- 新增功能 = 新增一个页签，不改动、不重排已有区块，回归面小。
- 每个页签可独立保存自身状态（滚动位置、分页页码、搜索词），互不干扰。
- 页签是浏览/编辑类面板的常见约定，学习成本低。

#### 3.1.2 可扩展的页签框架（本次就要按这个结构写）

本次只落地两个页签，但渲染与状态结构要写成“可注册的页签列表”，而不是写死两个分支：

```
state.editorTab = "edit" | "contacts" | ...

const EDITOR_TABS = [
  { id: "edit",     label: "编辑",       render: renderEditTab },
  { id: "contacts", label: "联系人列表", render: renderContactsTab },
];
```

规则：

- 页签栏由 `EDITOR_TABS` 生成，新增功能只往数组里加一项，不改布局代码。
- 每个页签自己负责内容渲染和自身状态；共享的只有 header、页签栏和滚动容器边界。
- 页签只负责内容，不放全局动作按钮；动作按钮统一收敛到预览区顶部工具栏（见 3.4），
  避免同一个按钮在不同页签语义不一致。

#### 3.1.3 必须先定的几个约束

1. 动作按钮归属（已确认）。
   - 「添加消息」从编辑面板 header 移到预览区顶部工具栏，与「群聊管理」同排（布置规则见 3.4）。
   - 编辑面板 header 只保留页签栏，页签内不再放全局动作按钮。
2. 滚动容器。
   - 现状是 `editor-header` sticky、整栏一起滚；页签化后要让**每个页签内容区各自滚动**，
     header 与页签栏固定，切换页签时各自保留滚动位置。
   - 注意右侧栏高度与 `overflow` 边界，不能让任一页签撑破 `.editor-column`。
3. 状态管理。
   - `state.editorTab` 记录当前页签。
   - 每个页签的临时状态单独存放（例如 `state.conversationListPage`、搜索词），不要塞进公共字段。
4. 无障碍。
   - 使用 `role="tablist"` / `role="tab"` / `role="tabpanel"`，并支持左右方向键切换。
   - 成本低，但要一开始就定，后期补会牵动 DOM。
5. 页签数量上限。
   - 3～5 个页签比较舒适；若未来功能超过 5～6 个，应改为“左侧图标导航 + 内容区”（类似 IDE 的 activity bar），
     而不是无限增加顶部页签。

#### 3.1.4 什么情况下不该用页签

- 两个功能区需要同屏对照（例如“消息列表”和“消息属性”当前就是联动关系，应留在同一页签内）。
- 内容短、且用户几乎总是全部看完的区块，保持堆叠比页签更省点击。
- 功能之间有强顺序依赖（步骤流程），用向导/步骤条而不是页签。

### 3.2 页签内列表分页

复用群组成员选择器已经验证过的分页模式：

- 分页大小**不沿用**群组成员的 8，改为按 `.editor-column` 实测尺寸适配（见 3.2.1）。
- 页脚显示「第 X / Y 页」与上/下页按钮。
- 只有条目数超过一页时才显示分页条。

每条卡片沿用现有 `contactAvatarHtml()` 头像渲染，保证角色/群组头像与预览一致。

#### 3.2.1 分页大小怎么定（实测）

用 Playwright 量了编辑面板与现有卡片（脚本一次性临时运行，不进回归）：

| 视口 | 编辑栏宽 | 编辑栏高 | 面板内卡片参考高度 | 卡片间距 |
| --- | --- | --- | --- | --- |
| 1280×800 | 260px | 800px | 52px（群组成员卡） | 8px |
| 1440×980 | 288px | 980px | 52px | 8px |
| 1920×1080 | 360px | 1080px | 52px | 8px |

可用列表高度 ≈ 编辑栏高 − 53px（header）− 页签栏 − 搜索行 − 分页条 − 上下内边距：

- 1440×980：约 763px ÷ 60px（52 卡 + 8 间距）≈ **12 条**
- 1280×800：约 583px ÷ 60px ≈ **9 条**

结论：写死 8 会在大屏留白，写死 12 会在小屏溢出。采用**按容器高度计算的动态分页**：

```
CONTACT_LIST_ROWS = clamp(floor(listViewportHeight / 60), 6, 16)
```

- 首次渲染前取不到高度时用默认 **8**，量到后立即重算。
- 监听容器尺寸变化（窗口缩放、页签重新可见）重算；重算后把当前页号夹回有效范围，避免停在空页。
- 卡片行高固定为 52px + 8px 间距，保证“几条 = 几行”可预测。

#### 3.2.2 页签内搜索

- 页签顶部放一个搜索框（`type="search"`），输入即时过滤，不请求后端。
- 匹配范围：联系人名字（`name`），大小写不敏感；群组同样按名字匹配。
- 搜索只改当前页签的筛选结果，**不影响**预览目录、发言人选人与群组流程。
- 过滤后重新计算页数；页码越界时回到第 1 页；搜索词留在 `state`（切页签不丢，刷新页面重置）。
- 无结果时给空状态提示，并保留搜索框内容以便直接改词。

### 3.3 与预览目录的关系

本次迁移后：

- 预览目录与右侧页签展示同一份“全部可会话角色”，行为不变。
- 右侧页签承担“浏览与进入”的职责，预览目录继续承担“切换当前会话”的职责。
- **预览目录本阶段保持原样**（仍渲染全部启用联系人）；页签改造完成后再单独处理它。

未来演进后：

- 右侧页签 = 来源（联系人列表，可分页、可搜索）。
- 预览目录 = 目标（会话列表，只显示双击加入的卡片）。
- 两侧通过 ID 列表联动，不复制联系人详情。
- 双击规则：来源卡片**双击**才加入会话列表；单击只用于浏览，不触发加入、不做高亮。

### 3.4 预览区顶部工具栏：添加消息与群聊管理

#### 3.4.1 现状

预览区顶部 `.preview-toolbar` 已是「左侧标题 + 右侧动作区」的水平布局：

- 左侧：`#previewTitle` 项目标题。
- 右侧：`.toolbar-actions`，`display: flex; gap: 10px`。

> 状态：本小节对应的改动**已完成**（先于页签改造落地）。
> `frontend/index.html` 中「添加消息」已从 `.editor-header` 移到 `.toolbar-actions`，
> 与「群聊管理」同排；`.editor-header` 只保留「编辑面板」标题。
> `.primary-button.compact` 与 `.secondary-button.compact` 统一为 32px 高、10px 内边距、12px 字号；
> `.toolbar-actions` 允许换行，窄屏下整条工具栏换行、两个按钮仍同排。
> 回归：`check_frontend.py`、`check_backend.py`、`check_project_store.py` 通过，Playwright `issues=[]`。

#### 3.4.2 结论：左右（同一行），不要上下堆叠

- 工具栏本身就是横向带，动作区已是横向 flex，加按钮零结构改动。
- 上下堆叠会撑高工具栏，把手机预览整体下推；预览是这一屏的主体，垂直空间最宝贵。
- 与现有约定一致：`sidebar-header`、`editor-header`、`modal-header` 都是「左标题 + 右动作」。
- 扩展性上横向更优：同排可容纳 3～4 个按钮，再多可收进「更多」菜单；上下堆叠并不会更能装，只会越长越高。

#### B.3 数据模型：`conversation_contacts.json` 升 `version: 2`

```json

  "updated_at": "2026-10-06T00:00:00Z",
  "contact_ids": ["…联系人列表来源，默认全部启用联系人…"],
  "preview_ids": [1084, 9001, 9002, "…"]
}
```

- `contact_ids`：阶段 A 已落地，语义不变 = 右侧「联系人列表」来源；本批不提供改它的 UI。
- `preview_ids`：本批新增 = 「会话列表」目标，有序、去重。
- 读取兼容：
  - 文件缺失 → `contact_ids` 默认全部启用；`preview_ids` 默认 `[薇儿丹蒂] + 全部内置群`。
  - 旧 `version: 1` 文件没有 `preview_ids` → 用上面的默认值，**不报错、不改写文件**。
  - `preview_ids` 指向已删除/已禁用联系人 → 读取时静默过滤（与 `contact_ids` 一致），不改写文件。
  - 只有真正写入才升 `version: 2`。
- 写入校验：非整数 / 布尔 / 未知或已禁用 ID → `400 invalid_request`；重复 ID 去重保序。
- `preview_ids` 的元素必须属于当前启用联系人（`contact_ids` 默认即全部启用，等价于“可会话联系人子集”）。
