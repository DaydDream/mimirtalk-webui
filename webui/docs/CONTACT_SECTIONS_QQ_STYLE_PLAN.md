# 联系人列表：QQ 式分类与自定义分组方向（备选，未开工）

> 状态：**仅记录方向，暂不实现**。本轮先按「方案 1：顶部筛选条」落地，
> 见 `CONTACT_DIRECTORY_RIGHT_PANEL_PLAN.md`。
>
> 记录时间：2026-10-06

## 1. 背景

右侧编辑面板的「联系人列表」页签当前是一条扁平列表 + 搜索 + 分页：

- 数据来源：`GET /api/conversation-contacts`（缺省回退 `/api/contacts`）。
- 排序：后端 `list_contacts()` 的顺序是「内置角色 → 内置群 → 自建群」，
  自建群是追加在最后的；前端 `filteredEditorContacts()` 不做排序。
- 结果：87 条数据（73 角色 + 10 内置群 + 4 自建群）分页后，用户自建群
  只能翻到最后几页才能看到，很难被直接发现。

期望的形态（参考 QQ 联系人页）：

1. 顶部保留「角色 / 群聊」这类一级分类（对应现有 `kind`）。
2. 一级分类内部改为可折叠的二级分组（QQ 的「朋友 / 同学 / 家人」），
   分组标题右侧显示数量，例如「自建群 4」。
3. 列表不分页，整列滚动。
4. 分组可由用户自行新增、重命名、删除、排序，联系人可被指派到分组。

## 2. 难度分档

### 2.1 A 档：去掉分页改滚动（简单）

- 现存分页是为「按面板高度倒推每页条数」服务的：
  `contactListPageSize()` 用 `#editorContactList.clientHeight / 60` 算行数，
  `renderEditorContactList()` 再切页，`ResizeObserver` 只负责窗口变化时重算。
- 改成整列表滚动后，这三处逻辑可以整体删除，页码状态、上下页按钮与
  `parseEditorContactPage` 相关断言一并去掉，属于**净减代码**。
- 87 条数据全部进 DOM 没有压力，不需要虚拟滚动。
- 需要重做的是视觉：现有卡片是「34px 头像 + 两行文字」的网格，
  QQ 是「箭头 + 名称 + 计数」的紧凑行。属于 CSS/模板工作。

### 2.2 B 档：固定三档分组 + 折叠（中等）

- 分组固定为「角色 / 内置群 / 自建群」，不需要改动数据模型，
  前端只靠 `kind` 与 `custom`（兜底 `asset_category === "custom_groups"`）推导。
- 前端 `state` 增加展开状态表，配合 `aria-expanded` 与箭头旋转。
- 自建群独立成组后可一眼看到，即可解决「找不到自建群」的问题。

### 2.3 C 档：用户自定义分组增删改（工作量最大）

真正的成本不在 UI，而在数据模型与持久化，需要先决定：

1. **一个联系人属于一个分组还是多个分组。**
   QQ 好友可同时在多个分组；这决定数据结构是 `contact -> section_id`
   还是一张多对多映射表，后期改动代价很大。
2. **分组是全局还是按项目。**
   现有 `conversation_contacts.json` 是全局单文件、与项目无关，分组大概率
   也应全局，需要明确，否则会出现同一角色在不同项目里属于不同分组。
3. **命名冲突。**
   后端已有 `custom_groups.json`，那是用户自建的**群聊**，不是分类。
   新功能建议使用 `sections` 或 `folders`，文件单独放
   `data/contact_sections.json`，避免与 `custom_groups` 混淆。
4. **边界情况。**
   删除分组时组内联系人如何处理（回「未分组」还是保留）、删除联系人后
   组内悬空 ID 如何清理、旧文件版本如何迁移。现有做法是读取时静默过滤
   无效 ID（见 `Application._load_conversation_contact_ids`），可沿用。
5. **指派交互是真正的难点。**
   拖拽最直观，但 HTML5 拖拽在触屏基本不可用；备选是「选择模式 + 多选指派」。
   这一步的交互设计成本高于新建/重命名/删除本身。
6. **联动面。**
   分类视图与左侧预览目录（阶段 B）、群聊管理、导出、发言人选人是否共用
   同一份名单，需要理清，否则同一角色会在不同视图表现不一致。
7. **测试。**
   `tools/check_ui_playwright.js` 的 `readEditorContactState` 对页签标签和页码
   有硬编码断言，分页断言需删除；后端需新增分组读写往返、非法输入、
   悬空引用过滤等断言。

工作量感受：C 档约为 B 档的 3～5 倍，大头在模型决策与指派交互。

## 3. 建议的分期

1. **第一步（低风险）**：去分页改滚动 + 固定三档分组 + 折叠 + 类别徽标。
   立即解决自建群难找的问题，同时验证滑动列表观感。
2. **第二步（需先定模型）**：新增 `data/contact_sections.json` +
   用户自定义分组的增删改。先做「新建 / 重命名 / 删除 + 菜单指派」，
   暂不做拖拽；模型稳定后再补拖拽排序。

## 4. 需要用户拍板的前置决策

1. 一个角色能否属于多个分组？
2. 分组是全局还是按项目？
3. 「未分组」如何展示？
4. 是否保留「角色 / 群聊」一级页签，还是被自定义分组完全替代？

## 5. 与现有设计的关系

- 与「方案 C 清单文件」不冲突：`conversation_contacts.json` 负责
  「哪些联系人可会话」，分组是另一维度，建议独立文件。
- 不走分页后，此前评估方案 4 时列出的「分页 × 面板高度自适应用户态互相影响」
  这一隐患会自行消失。
- 一级页签（`EDITOR_TABS`）与二级分组必须在 DOM 与状态上分开命名
  （例如分组按钮用 `data-contact-section`，不复用 `data-editor-tab`），
  否则会命中一级页签的点击委托与键盘导航。
